Found a few real bugs, one of which will actually reproduce daily for your actual users. Here's the breakdown:

Highest priority — timezone date bug that will misfire every evening. Both `app/(tabs)/index.tsx` (line 56, `todayYMD`) and `components/RescheduleModal.tsx` (`toYMD()`) build their "today's date" string using `new Date().toISOString().split('T')[0]`. `toISOString()` always converts to UTC — and since your studio operates in America/New_York (UTC-4/-5), any user with their phone set to Eastern time will have this roll over to tomorrow's date once local time passes roughly 7-8pm. Concretely: the dashboard's "today's sessions" filter will silently show empty in the evening even when a session is scheduled for that night, and the reschedule modal's date picker/availability fetch will be misaligned with what the studio actually considers "today." Fix: build the YMD string from local `getFullYear()`/`getMonth()`/`getDate()` instead of `toISOString()`.

Certificate dollar-sign display bug in `book.tsx`. The code decides whether to show a "$" prefix using `/^\d/.test(cert.remainingValue)` — but both a session-count string like `"3 sessions"` and a raw dollar string like `"45.00"` start with a digit, so the regex can't tell them apart. Dollar-value certificates will render as `"45.00 remaining"` instead of `"$45.00 remaining"`, in both the packages list and the certificate banner. This needs an actual type/shape check from the API (e.g., a boolean flag) rather than a regex guess on the formatted string.

Biometric sign-in stores and replays the real password. `useBiometrics.ts` saves the user's plaintext email+password in SecureStore, and `sign-in.tsx`'s `handleBiometricSignIn` sends that stored password straight back into Clerk's `signIn.create()` on every biometric unlock. Since Clerk already persists its own session via `expo-secure-store` (set up in `_layout.tsx`), this is redundant and riskier than it needs to be — it stores a secret that doesn't need to exist at all, and it's why you need special-case handling for `form_password_pwned`/`form_password_incorrect` errors when the stored password goes stale. A session-gate pattern (use biometrics to unlock access to the already-active Clerk session, not to re-authenticate with a stored password) would be both simpler and safer.

Worth confirming — `/api/booking/config`. `book.tsx`'s booking screen calls this endpoint for `ownerId`, `appointmentTypes`, and per-location `calendarId`. I don't have your current api-server code in this upload to confirm it exists — when I reviewed the api-server before, there was no such endpoint, and the `/api/booking/locations` route had an explicit comment that calendar IDs "stay server-side and are never exposed to the client." If that endpoint doesn't actually exist yet server-side, the booking screen will fail to load configs entirely. If it does exist, that's a deliberate reversal of the earlier design (probably fine, calendar IDs aren't sensitive, but worth confirming it's intentional rather than a leftover).

Minor: the certificate-code input has a 600ms debounce before validation completes — a user who types a code and immediately taps a location card could book before `status` reaches `'valid'`, silently leaving the certificate unapplied. Also, certificate codes are persisted via plain `AsyncStorage` rather than `SecureStore` — lower stakes than the password issue, but same category of "storing something locally that doesn't need unencrypted storage."

Good things worth noting: the reschedule flow itself (loading/error/disabled states, cancel-in-flight guards) is solid, the deep-link handler is well thought through with a sensible fallback, and the notification-scheduling hook correctly cancels stale reminders before rescheduling and gracefully no-ops in Expo Go.
