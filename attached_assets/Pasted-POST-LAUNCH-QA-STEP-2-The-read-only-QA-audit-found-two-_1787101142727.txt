ISSUE 2 — Server-side location/service compatibility

The booking API currently validates the selected location/calendar but does NOT independently verify that the submitted appointmentTypeID belongs to that location.

Fix this server-side.

Use the existing Acuity location configuration as the source of truth:

- Potomac: appointmentTypeIDs configured for Potomac
- Kentlands: appointmentTypeIDs configured for Kentlands

Before calling Acuity from POST /api/booking/appointments:

1. Resolve the requested location.
2. Resolve the requested appointmentTypeID.
3. Verify that the appointmentTypeID is included in that location's configured appointmentTypeIDs.
4. If it is not compatible, reject the request locally.
5. Return a clear 4xx error.
6. Do NOT call Acuity for an incompatible location/service combination.

Do not hardcode appointment type IDs into the route. Use the existing location configuration.

The normal valid combinations must continue to work:

- Potomac + Workout for 1 → allowed
- Kentlands + Workout for 1 → allowed
- Kentlands + Red Light Therapy → allowed when client eligibility permits it
- Potomac + Red Light Therapy → rejected server-side
- Any other appointmentTypeID not configured for the selected location → rejected server-side

Important:
This server-side check is defense-in-depth. Keep the existing client-side certificate eligibility filtering exactly as it is.
