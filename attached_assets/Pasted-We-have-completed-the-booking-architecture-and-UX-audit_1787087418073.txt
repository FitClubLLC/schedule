We have completed the booking architecture and UX audit.

Do NOT redesign the entire application.

This task is specifically to restructure the native booking flow before visual polish.

The target member journey is:

BOOK
→ LOCATION
→ SERVICE (only when necessary)
→ DATE + TIME
→ CONFIRM
→ CONFIRMED

The major change is to combine the current SelectDate and SelectTime screens into a single Date + Time experience.

## IMPORTANT

Preserve all existing backend/API behavior.

Do not modify:

* Acuity authentication
* Booking API
* Certificate validation rules
* Availability APIs
* Cancellation
* Rescheduling
* Free Trial
* Appointment creation logic

Do not change business rules.

## 1. Create a combined Date + Time experience

Replace the conceptual two-screen flow:

SelectDate
→ SelectTime

with:

SelectDateTime

The existing SelectDate and SelectTime logic should be reused rather than duplicated.

The new screen should:

1. Load available dates exactly as SelectDate currently does.
2. Display the calendar.
3. When a date is selected, fetch available times using the existing availability hook.
4. Display available times for that selected date.
5. Preserve the exact Acuity datetime value.
6. Allow the member to change dates and automatically refresh the available times.
7. Clear the selected time when the date changes.
8. Clear the selected time if the previously selected slot is no longer available.
9. Continue to Confirm with the selected datetime.

Do not combine the backend API calls. They should remain separate internally.

## 2. Desktop layout

For desktop/tablet:

Use a two-column layout.

LEFT:
Calendar

RIGHT:
Available times for selected date

Before a date is selected, the right panel should show a simple instructional empty state:

"Choose a date"
"Select an available date to see appointment times."

After selecting a date:

"THURSDAY, AUGUST 20"

Then group times into:

MORNING
AFTERNOON
EVENING

Only display groups that contain available slots.

Do not invent times or availability.

## 3. Mobile layout

For mobile:

Calendar first.

Then available times below the calendar.

After a date is selected, scroll/focus the user toward the available times if this can be done cleanly without causing accessibility problems.

The primary Continue CTA should be sticky at the bottom of the viewport.

The CTA should be disabled until a valid time is selected.

Do not allow the calendar or time list to be obscured by the sticky CTA.
